## Bottom line / evidence boundary

**A bounded browser-local NLI experiment is credible; reliable clinical classification and the two-second warm target are unproven.** Existing ONNX artifacts avoid an initial model-conversion project. DeBERTa-xsmall below merits a compatibility/accuracy experiment; MobileBERT offers a smaller comparison **conditional on license clarification**. Neither is selected for implementation. An embedding-only baseline is possible but semantic similarity is not evidence that an intervention occurred or that a response relates to it.

This is documentation/source/artifact-metadata research, **not a benchmark**: no weights downloaded, inference executed, accuracy measured, laptop characterized, or offline browser behavior verified. Listed bytes are publisher artifact metadata, not measured transfer size or memory. Publisher results on other tasks/hardware are not LQA evidence. No clinical examples or suggestion copy were generated.

Scope remains the four note-only checks across all active fields: performed intervention **and** relevance to presenting need; response linked to that intervention; specific next steps **or** appointment/scheduling plan; progress including lack of progress/no change. Service-code/scope verification is excluded. Every result is pass/fail, ambiguity leans fail under Tim's rubric. Preparation/resource failure is different from classification uncertainty; do not silently use keywords for uncertain scores.

## What might “Jev” mean?

Identity remains **unconfirmed**; ask for the user's original link only if pursuing this family. Search found several distinct projects, not interchangeable vendors/models:

- **TypeSafe AI's Jev:** first-party [introduction](https://docs.typesafe.ai/introduction) and [model documentation](https://docs.typesafe.ai/models) describe typed Choice/Score/Noul decisions through a hosted `POST /v1/systemone` API. The examined model page names `jev-1.13.0`; aliases move. It supplies no downloadable ONNX/browser artifact or local-weight license. **Browser-local eligibility is not established**; a JavaScript SDK calling an API is not local inference. Its calibration and speed claims do not establish performance on these notes. Its [confidence documentation](https://docs.typesafe.ai/confidence) explicitly describes confidence as a statistic of the output distribution and asks users to test domain-specific thresholds.
- **Featherless Simple Jev:** [owner repository](https://github.com/featherless-ai/simple-jev) describes next-token-logit classification using compatible open models, with a **Python/PyTorch local server**, not browser inference. Server-side local operation and a web playground do not satisfy Chrome-local execution. Underlying model license, size, context, and a browser port would all need separate checking; no browser-ready artifact was established here.
- **JevEmbed:** [owner repository](https://github.com/HITsz-TMG/JevEmbed) explicitly describes an embedding-based Python framework with optional HTTP server. It offers multiple base/fine-tuned embedding models with different limits; its browser playground is served by Python. It is a plausible match to an “embeddings” recollection, **not evidence of the intended identity** or of a Chrome-local implementation. No single size/license applies to all its backends.

Search also surfaced similarly named explainer/marketing domains. They were not treated as proof of ownership or authority; conclusions above rely on project owners. No hosted service was called with note data.

## NLI is a starting approach, not calibrated confidence

The examined [Transformers.js 3.8.1 implementation](https://github.com/huggingface/transformers.js/blob/3.8.1/src/pipelines.js) pairs a premise with one hypothesis per candidate label:

- Default `multi_label: false` normalizes entailment logits **across labels**. That would incorrectly make the four independent checks compete; a highest score exists even when no check is supported.
- `multi_label: true` (also a single candidate) normalizes entailment versus contradiction per hypothesis. It recognizes `not_entailment` for the binary DeBERTa model. With three-way MobileBERT it **omits neutral from that two-logit normalization**: a high returned score is not necessarily strong evidence against neutrality. Inspect raw logits/three-way outputs in the prototype rather than assuming a safe threshold.
- This version loops over premises and hypotheses with awaited model calls. Passing four labels is **not automatically one batched forward pass**. Compound criteria or chunking increase the number of inferences. Direct model batching may be worth a separate measured comparison, not an assumed optimization.
- The pipeline tokenizes with `truncation: true`. A 512-token pair includes note text, hypothesis and special tokens, not 512 note words. Silent tail loss can discard an appointment or contradicting statement. Preserve field boundaries, measure actual token counts, and explicitly reject/out-of-envelope or evaluate a reviewed chunking policy; maximum chunk-score aggregation can manufacture a pass from incomplete evidence.

Recommendation for the experiment: compare whole-note hypotheses to explicitly decomposed criteria where the rubric requires AND/OR relationships; keep the decomposition and aggregation fixed before holdout evaluation. Hypothesis wording, field ordering, quantization and backend are experimental variables. Zero-shot needs no new training set to **run**, but reviewed labels are essential to assess reliability and tune a decision policy. Softmax, cosine similarity, entropy or vendor “confidence” is not automatically a calibrated probability of a correct clinical judgment. No score threshold or acceptable error rate is chosen here.

## Browser/runtime feasibility and limitations

The versioned [Transformers.js WebGPU guide](https://huggingface.co/docs/transformers.js/v3.8.1/guides/webgpu) documents `device: 'webgpu'`; [ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/) offers WASM CPU inference and only a subset of operators on GPU backends. Existing ONNX weights and architecture support do **not** establish that a particular quantized graph loads/runs on WebGPU. Probe the exact model/dtype/backend combination; do not promise automatic recovery from WebGPU initialization or device loss.

- Chrome's [platform overview](https://developer.chrome.com/docs/web-platform/webgpu/overview) records desktop rollout in Chrome 113 on supported Windows/ChromeOS/macOS hardware. Its page is dated August 2025 and is not a current exhaustive compatibility matrix. Feature-detect an adapter/device and perform actual model initialization on Tim's current Chrome/OS/GPU; browser version alone is insufficient. No unsafe flags should be assumed for the supported demo envelope.
- [Deployment requirements](https://onnxruntime.ai/docs/tutorials/web/deploy.html): WebGPU needs a secure context (HTTPS or localhost); ship the required JS, WASM and worker assets, not just weights. Match WASM binaries to the JS runtime build. Cross-origin model/CDN fetches and deployment CSP must be tested.
- [ORT flags](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html): WASM multithreading requires browser support and `crossOriginIsolated`; single-thread WASM remains a comparison path. Verify hosting/isolation headers and external-asset compatibility rather than assuming localhost performance transfers to deployed hosting.
- Put tokenization/model loading/inference in a dedicated worker to keep editing usable. ORT's **WASM proxy worker is not the same as an application worker** and cannot be used with its WebGPU execution provider. The deployment and flags pages differ in their broad CSP descriptions; validate the exact version, worker loading mode and deployed CSP.
- Warm-up is real inference, potentially compiling kernels/allocating buffers. Weight transfer size does not predict CPU/GPU peak memory, session startup or warm latency. Reusing a live session avoids repeated initialization; a cached download does not preserve a live worker/session across reloads. Long inputs, shape changes, multiple tabs and device loss remain experiment cases.

The runtime facts above use an explicitly examined **3.8.1** source/doc baseline, not a claim that it is the newest release. Pin whichever runtime is actually tested; do not mix main-branch documentation with a release silently.

## Cache, progress and readiness: concrete constraints

First-party [environment API](https://huggingface.co/docs/transformers.js/v3.8.1/api/env), [3.8.1 loader source](https://github.com/huggingface/transformers.js/blob/3.8.1/src/utils/hub.js), [pipeline source](https://github.com/huggingface/transformers.js/blob/3.8.1/src/pipelines.js), and browser [storage documentation](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) establish:

1. **Model caching is not full-app offline support.** `useBrowserCache` uses Cache API when available; this version opens `transformers-cache` and normally keys remote artifacts by URL including revision. `cacheDir` is filesystem caching, not a browser disk directory. Cached weights do not guarantee the HTML, JS chunks, worker, tokenizer/config and ORT WASM are available on offline reload. A loaded tab running offline, cached-model reload and full offline navigation are different tests.
2. **Do not persist a boolean as readiness proof.** Cache opening can fail and loading proceed without cache; cache writes can warn on quota failure while inference still succeeds. “Ready this session” and “verified reusable resources” therefore differ. Revalidate the complete resource manifest and initialize/warm the session after reload before marking enhanced checking usable. Network-disabled replay is the offline proof, not `navigator.onLine` or a previous callback.
3. **Progress is version-specific.** In examined 3.8.1 the loader emits per-file `initiate`, `download`, `progress`, `done`; pipeline `ready` follows loading, not a warm inference. Cache reads can emit download/progress events too. Newer [HF reference material](https://github.com/huggingface/skills/blob/main/skills/transformers-js/references/PIPELINE_OPTIONS.md) mentions `progress_total`; do not assume it exists in 3.8.1. Use known manifest sizes for weighted byte progress, or indeterminate status when totals are unavailable. File download 100% must not masquerade as session initialization/warm-up completion. Runtime asset fetching may need separate instrumentation.
4. **Storage is best-effort by default**, shared per origin (including port), subject to quota, storage pressure and user deletion. Incognito storage is usually deleted on exit. `navigator.storage.estimate()` is an estimate, not reserved space. `persist()` may be granted or denied automatically in Chrome and cannot prevent deliberate user clearing. A new dev-server port/deployment hostname is a different cache origin.
5. **Version the entire preparation bundle.** Use immutable model revisions/URLs plus dtype, tokenizer, runtime/WASM and rule/hypothesis version. Default `main` URLs can reuse old cached files; do not equate them with freshness. A manifest must become usable only when complete and successfully exercised. Keep old/new resources distinct during preparation; clean obsolete owned artifacts deliberately, not unrelated origin data. Budget disk for overlapping versions and transient memory copies. Exact cleanup/rollback policy belongs to #106.
6. **Partial preparation is not resumable by promise.** Complete files may be reusable, but byte-range resume/cancellation guarantees were not established. Test interruption, missing tokenizer, truncated/corrupt weights, cache denial, retry and simultaneous preparation. `local_files_only`/`allowRemoteModels` are loader controls, not an offline guarantee for the rest of the application; 3.8.1 also requires compatible `allowLocalModels` settings and may try same-origin local paths. Verify with blocked network and request logs.

Suggested distinction for #106 (not a finalized UX): not prepared → downloading → initializing → warming → ready-for-this-session; independently record cache verification/persistence status. On preparation failure keep legacy usable. Snapshot the engine and note at a Check Quality click; later readiness only affects later clicks. A runtime failure needs the agreed run-level policy, never partial enhanced results blended invisibly with keyword results. Low classifier confidence remains a separate pass/fail policy, not a preparation error.
