Git, the shared way.
One main, zero surprises.

This repository is shared across Designers & PMs, Sales, and Developers. Each team has its own workflow, but everyone follows the same core rules to keep main stable and demo-ready at all times.

All Git operations are done through Claude Code — no terminal commands required.

The five

Core rules everyone follows.

Memorize these. They're what keep main calm while three teams work in parallel.

01
Never push directly to main.
All changes go through a Pull Request.
02
Start from the latest main.
Sync before branching so you're not on stale code.
03
Keep branches short-lived.
One branch per task. Merge or discard when done.
04
Write a one-line PR description.
A sentence on intent helps reviewers move fast.
05
One dev approval to merge.
Tag a developer; they sign off, you ship.

Designers & PMs

Prototype upcoming features without stepping on Sales or Devs.

Your branch is your sandbox. Experiment freely — main is protected, and the work you ship for review is exactly the work you mean to ship.

Workflow
  1. Ask Claude Code: "Create a new branch called prototype/[your-feature-name] from main."
  2. Make your changes — Claude Code handles the code.
  3. When ready for feedback: "Open a pull request for this branch."
  4. Add a one-line description of what the prototype is exploring.
  5. Tag a dev to review.
Things to know
Your branch is your sandbox — feel free to experiment.
Need a fix from main? Ask Claude Code: "Sync my branch with the latest main."
Don't worry about breaking things on your branch — that's what it's for. Main is protected.
Sales

Maintain a clean, impressive demo that's always ready to present.

A prospect should never see anything you didn't choose to show. Branch the demo, control the surface area, sync before you walk in the room.

Workflow
  1. Ask Claude Code: "Create a new branch called demo/[demo-name] from main."
  2. Make any customizations needed for the demo.
  3. When ready: "Open a pull request for this branch."
  4. Add a one-line description (e.g., "Customized for Q2 enterprise pitch — added placeholder org data").
  5. Tag a dev to review before presenting.
Things to know
For recurring demos, you can reuse a branch — just sync it with main before each presentation.
Custom look for one prospect? Create a new branch rather than modifying an existing demo branch.
Never demo directly from main — always present from your own branch so you control what's shown.
Developers

Ship features and fixes — keep main stable for everyone else.

You build it, you review it, you keep the standard. Non-dev PRs need a quick sanity check, not a deep code review.

Workflow
  1. Branch off main: feat/your-feature or fix/your-fix
  2. Build and test.
  3. Open a PR, get one peer approval, merge.
  4. After merging, let the other teams know if they should sync their branches.
Reviewing non-dev PRs
Quick sanity check, not a deep review — 5 minutes or less for most non-dev PRs.
Does it do what the description says?
Does it break anything in main or other active branches?
Is there anything that would embarrass us in a demo or presentation?
For reviewers

Five minutes is enough.

You're not deep-reviewing prototype code or demo tweaks. You're catching the few things that actually matter — described behavior, blast radius, public-facing risk.

Questions?
